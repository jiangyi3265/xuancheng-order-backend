# 上线前补丁包 · 线上升级清单

适用：把线上接单系统（https://jiedanxt.oksja.cn/）升级到带“回收站、操作日志、改密码、导出 Excel、自动备份”的版本。
代码在三个仓库的 `feat/hardening-v1` 分支：`xuancheng-order-backend`、`xuancheng-order-admin`、`xuancheng-order-app`。

> **这个分支建立在“权限升级”（`feat/permission-v1`）之上。** 线上如果还没做权限升级，两个包要一起上线，先看 `权限升级清单.md`，再回到本清单。
> 服务器目录、服务名沿用 `production.md`。本清单没有连过服务器，涉及服务器现状的地方都标了“先确认”，请先核对再动手。
> 预计影响：后端重启约 1 分钟，期间后台和客户端会短暂打不开。建议选没人用的时段。

---

## 一、这次升级带来什么

| 项目 | 变化 |
| --- | --- |
| **堵住匿名上传漏洞** | 原来任何人不用登录就能往服务器上传文件（每个有大小限制，但次数不限，可以慢慢把磁盘塞满）。现在必须是后台账号或客户账号才能上传。**这条最重要：线上现在运行的版本有这个洞。** |
| 回收站 | 删除项目不再是真删，先进回收站，可恢复；只有总管理员能“彻底删除”。客户撤回的项目也进回收站 |
| 客户删除受限 | 客户只能撤回还在“待确认”的问题；团队开始处理后不能再自行删除（防止聊天记录、Bug、内部记事本被一键清空） |
| 操作日志 | 总管理员可查：谁、什么时候、对什么项目/账号做了什么（删除、改金额、转派、改状态、账号管理、导出、改密码）。日志写失败不会影响业务 |
| 修改密码 | 后台右上角钥匙图标、客户端「我的项目」页的“修改密码”。改完其他设备自动退出 |
| 订单列表 | 新增筛选（收款、逾期、创建日期）、列表分页、导出 Excel；看板“已完成”列只显示最近 30 个。后台每 10 秒只问一个很轻的“变更戳”，有变化才重新拉列表 |
| 附件安全 | SVG 等附件直接打开时不能执行脚本；未知类型一律当下载处理 |
| 上传大小 | 后端的上传上限从 10MB 提到 50MB，与代码和 Nginx 一致（原来超过 10MB 的视频会传不上去） |
| Druid 监控页 | 默认关闭（原默认账号密码 ruoyi/123456 是公开已知的） |
| 自动备份 | `deploy/backup.sh`：每天备份数据库 + 附件增量镜像 + 自动清理 + 可选恢复演练 |
| 清理 | 删除了仓库里带默认密码的旧演示 SQL、已退役的旧服务器维护流程、过期文档和没人用的旧代码 |

## 二、动手前先定下来

- [ ] 升级时段。
- [ ] 备份放哪里：**除了服务器本机，最好再有一个地方**（另一块盘 / 挂载的网盘 / 另一台机器）。想好目录，下面第五步 6 会用到。
- [ ] 如果线上还没做“权限升级”：先定好下属管理员是谁（见 `权限升级清单.md` 第一节）。

## 三、服务器上先确认（只读，不改任何东西）

连数据库的方式与 `mysqldump` 相同：`--defaults-extra-file=/opt/xuancheng-order/config/mysql-root.cnf`，库名 `xc_jiedan`。

- [ ] **Nginx 的上传上限**：站点配置 `/www/server/panel/vhost/nginx/jiedanxt.oksja.cn.conf` 里 `client_max_body_size` 不能小于 `55m`。没有这一行或者更小，就加/改成 `55m`，`nginx -t` 通过后重载。
- [ ] **生产配置有没有单独写上传上限**：
  ```bash
  grep -n -i "max-file-size\|max-request-size\|profile\|statViewServlet\|login-password" /opt/xuancheng-order/config/application-production.yml
  ```
  - 如果出现 `max-file-size: 10MB`，改成 `50MB`、`max-request-size` 改成 `55MB`（否则这次的提升不会生效）。
  - 记下 `profile:` 的路径——这是上传文件放的地方（文件在其下的 `jiedan-media/` 里），备份脚本要用（第五步 6）。
  - 如果看到 `statViewServlet` 且 `enabled: true`，改成 `false`。
- [ ] **验证码现状**：`SELECT config_value FROM sys_config WHERE config_key='sys.account.captchaEnabled';`
  安装脚本默认是 `false`（关）。关着的情况下，防暴力破解靠 RuoYi 自带的“连续输错 5 次锁定 10 分钟”，对内部使用够用；如果要开，把值改成 `true` 并重启后端，登录页会自动出现验证码。
- [ ] 当前线上登录正常、能看到订单（基线）。

## 四、备份（必须）

```bash
mkdir -p /opt/xuancheng-order/backups
mysqldump --defaults-extra-file=/opt/xuancheng-order/config/mysql-root.cnf \
  --single-transaction xc_jiedan \
  > /opt/xuancheng-order/backups/xc_jiedan_before_hardening_v1_$(date +%F_%H%M).sql
ls -lh /opt/xuancheng-order/backups | tail -3
```

- [ ] 备份文件生成且大小正常（不是 0）。
- [ ] 记下当前 `current` 指向哪个版本目录（回滚要用）：`readlink /opt/xuancheng-order/current`

## 五、上线（顺序不能乱）

1. [ ] **本机构建**（三个仓库都切到 `feat/hardening-v1` 分支）
   ```bash
   cd xuancheng-order-admin && npm ci && npm run build                          # 产物 dist/
   cd xuancheng-order-app && npm ci && VITE_BASE=/client/ npm run build         # 产物 dist/
   cd xuancheng-order-backend && mvn -B clean package -DskipTests               # 产物 ruoyi-admin/target/ruoyi-admin.jar
   ```
   确认用的是新分支的产物：在后台 `dist/` 里执行 `grep -l 操作日志 dist/assets/*.js`，能搜到文件。
2. [ ] **执行升级 SQL**（只新增字段和表，旧版后端不受影响，可重复执行）
   把 `deploy/upgrade_hardening_v1.sql` 传到服务器后：
   ```bash
   mysql --defaults-extra-file=/opt/xuancheng-order/config/mysql-root.cnf xc_jiedan < upgrade_hardening_v1.sql
   ```
   检查：`SHOW COLUMNS FROM jiedan_order LIKE 'del_flag';` 有结果；`SHOW TABLES LIKE 'jiedan_audit_log';` 有结果。
3. [ ] **新建版本目录并放入新产物**：在 `releases/` 下新建目录，放入后台 `dist`（作为 `admin/`）、客户端 `dist`（作为 `admin/client/`）、新的 `ruoyi-admin.jar`（作为 `backend/`）。**不要动** `data/`、`uploads/`、`config/`。
4. [ ] 如果第三步确认里需要改 Nginx 或 `application-production.yml`，现在改好。
5. [ ] **原子切换 `current`，重启后端**：
   ```bash
   systemctl restart xuancheng-order-backend
   nginx -t && nginx -s reload      # 或用宝塔重载 Nginx
   ```
6. [ ] **安装自动备份**
   ```bash
   mkdir -p /opt/xuancheng-order/bin
   cp backup.sh /opt/xuancheng-order/bin/backup.sh && chmod +x /opt/xuancheng-order/bin/backup.sh
   # 手动跑一次，确认成功（把下面两个路径换成第三步确认到的真实路径；OFFSITE_DIR 换成你选的异地目录，没有就先不写）
   XC_UPLOADS=<profile 路径> OFFSITE_DIR=<异地目录> /opt/xuancheng-order/bin/backup.sh
   ```
   看到“数据库备份完成”“附件镜像完成”且没有“失败”即可。然后在宝塔「计划任务」（或 `crontab -e`）加两条（环境变量写在命令前面）：
   ```
   30 3 * * *  XC_UPLOADS=<profile 路径> OFFSITE_DIR=<异地目录> /opt/xuancheng-order/bin/backup.sh >> /opt/xuancheng-order/logs/backup.log 2>&1
   0 4 * * 0   VERIFY_RESTORE=1 XC_UPLOADS=<profile 路径> OFFSITE_DIR=<异地目录> /opt/xuancheng-order/bin/backup.sh >> /opt/xuancheng-order/logs/backup.log 2>&1
   ```
   第二条每周日做一次“恢复演练”：把当天的备份真的导入一个临时库、数一数订单、再删掉临时库。**没演练过的备份不算备份。**

## 七、回滚

**只做了第 2 步（SQL）**：不用回滚，新字段和新表旧版后端不会用到。

**已切换版本，要退回旧版**：
1. 把 `current` 切回升级前记下的版本目录，`systemctl restart xuancheng-order-backend`，重载 Nginx。
2. ⚠️ 旧版后端不认识“回收站”：**已经放进回收站的项目，退回旧版后会重新出现在列表里**（因为旧版不知道它们被删过）。退回前先在回收站里把需要的恢复、不要的彻底删除，或者接受它们重新出现。
3. 退回旧版后，匿名上传漏洞会重新出现，请尽快修好后再升级。
4. 数据乱了：用第四步的备份恢复（升级后新增的订单会丢，先导出再恢复）。

## 八、你需要在 GitHub / 服务器上亲自做的事（我没有动，也不会替你动）

- [ ] **把三个仓库改成私有**（backend / admin / app）：GitHub → 仓库 → Settings → 最下面 Danger Zone → Change visibility → Make private。里面有部署目录、端口、历史提交里的演示账号等信息，不该公开。
- [ ] **删除仓库里旧的服务器密钥**：backend 仓库 Settings → Secrets and variables → Actions，把 `SERVER_HOST`、`SERVER_USER`、`SERVER_PASSWORD`、`SERVER_PORT` 删掉。这次分支已经删除了用到它们的 6 个旧维护流程文件，但**合并到主分支之前**那些流程仍然能被运行。
- [ ] **旧服务器（`kejijava`）的登录密码改掉**。旧流程里用过它，仓库曾经公开过，应当视为已泄露。
- [ ] `xuancheng-ai-pipeline` 仓库（已退役）：Settings → Archive this repository。
- [ ] 仓库公开期间提交过的演示账号（`admin/admin123`、`customer/customer123`）：确认线上没有这些账号或已改密码。

## 九、已知限制

- 回收站里的项目不会自动清理，需要总管理员手动“彻底删除”。操作日志没有保留期限，会一直累积（每条很小，内部使用的量级没有问题）。
- 订单列表的分页是在浏览器里做的：后台仍然会把“我能看到的全部项目”载入一次，之后只在有变化时才重新载入。项目到几千个以内没有问题；再多就需要改成服务端分页。
- 导出的是当前筛选结果的全部项目（没有条数上限）；需求说明过长会被截成 2000 字。
- 审批流程（下属提验收/改报价，总管理员批）还没做。
- 附件的访问链接依然是公开的（靠随机文件名保护），不按订单归属拦截，与升级前一致；本次只是让它们直接打开时不能执行脚本。
