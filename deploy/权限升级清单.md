# 权限升级 V1 · 线上升级清单

适用：把线上接单系统（https://jiedanxt.oksja.cn/）从“一个共用 admin 账号”升级为“总管理员 / 下属管理员”。
代码在三个仓库的 `feat/permission-v1` 分支：`xuancheng-order-backend`、`xuancheng-order-admin`、`xuancheng-order-app`。

升级后的效果：总管理员看全部项目；下属管理员只看负责人是自己的项目；客户提交的需求自动落到其归属管理员名下。审批流程是第二步，本次不含。

> 服务器目录、服务名沿用 `production.md`。本清单没有连过服务器，涉及服务器现状的地方都标了“先确认”，请先核对再动手。
> 预计影响：后端重启约 1 分钟，期间后台和客户端会短暂打不开。建议选没人用的时段。

---

## 一、动手前先定下来（需要你决定）

- [ ] 下属管理员是谁：登录账号（字母/数字/下划线）、姓名、初始密码。默认按“原来的副总裁 费鹏飞”处理，旧订单里原来归副总裁的单会转给他。
- [ ] 总管理员就是现在的 `admin` 账号（或你实际在用的那个管理员账号）。
- [ ] 升级时段。

## 二、服务器上先确认（只读，不改任何东西）

连数据库的方式与 `mysqldump` 相同：`--defaults-extra-file=/opt/xuancheng-order/config/mysql-root.cnf`，库名 `xc_jiedan`。

- [ ] **总管理员账号确实拥有 admin 角色**，并看清有几个：
  ```sql
  SELECT u.user_id, u.user_name, r.role_key
    FROM sys_user u
    JOIN sys_user_role ur ON ur.user_id = u.user_id
    JOIN sys_role r ON r.role_id = ur.role_id
   WHERE r.role_key IN ('admin','employee');
  ```
  期望：只有你的管理员账号，角色是 `admin`，没有 `employee`。如果有多个 admin 账号，它们都会被当成总管理员（都能看全部、都会收到提醒）。
- [ ] **旧订单的负责人只有 1 和 2**：
  ```sql
  SELECT owner_id, COUNT(*) FROM jiedan_order GROUP BY owner_id;
  ```
  期望只出现 `1`、`2`（或 NULL）。出现别的数字，先别动，找我看。
- [ ] **用户 id 1、2 没被别人占用**：
  ```sql
  SELECT user_id, user_name FROM sys_user WHERE user_id IN (1,2);
  ```
  id 1 应当是总管理员；id 2 要么不存在，要么就是你准备当下属的那个人。否则迁移脚本会把别人的单误改，先找我。
- [ ] 当前线上登录正常、能看到订单（基线）。

## 三、备份（必须）

```bash
mkdir -p /opt/xuancheng-order/backups
mysqldump --defaults-extra-file=/opt/xuancheng-order/config/mysql-root.cnf \
  --single-transaction xc_jiedan \
  > /opt/xuancheng-order/backups/xc_jiedan_before_permission_v1_$(date +%F_%H%M).sql
ls -lh /opt/xuancheng-order/backups | tail -3
```

- [ ] 备份文件生成且大小正常（不是 0）。
- [ ] 记下当前 `current` 指向哪个版本目录（回滚要用）：`readlink /opt/xuancheng-order/current`

## 四、本机构建（三个仓库都切到 `feat/permission-v1` 分支）

```bash
# 后台管理
cd xuancheng-order-admin && npm ci && npm run build          # 产物 dist/
# 客户端（注意 VITE_BASE）
cd xuancheng-order-app && npm ci && VITE_BASE=/client/ npm run build   # 产物 dist/
# 后端
cd xuancheng-order-backend && mvn -B clean package -DskipTests         # 产物 ruoyi-admin/target/ruoyi-admin.jar
```

- [ ] 三个构建都成功。
- [ ] 确认用的是新分支的产物：在后台 `dist/` 里执行 `grep -l 成员管理 dist/assets/*.js`，能搜到文件。

## 五、上线（顺序不能乱）

1. [ ] **先执行升级 SQL（只新增表和角色，旧版后端不受影响，可重复执行）**
   把 `deploy/upgrade_permission_v1.sql` 传到服务器后：
   ```bash
   mysql --defaults-extra-file=/opt/xuancheng-order/config/mysql-root.cnf --default-character-set=utf8mb4 xc_jiedan < upgrade_permission_v1.sql
   ```
   检查：`SELECT role_id, role_key FROM sys_role;` 多了 `employee`；`SELECT * FROM jiedan_account_owner;` 里每个现有客户账号都归到总管理员名下。
2. [ ] **新建版本目录并放入新产物**：在 `releases/` 下新建目录，放入后台 `dist`（作为 `admin/`）、客户端 `dist`（作为 `admin/client/`）、新的 `ruoyi-admin.jar`（作为 `backend/`）。**不要动** `data/`、`uploads/`、`config/`。
3. [ ] **原子切换 `current`，重启后端**：
   ```bash
   systemctl restart xuancheng-order-backend
   nginx -t && nginx -s reload      # 或用宝塔重载 Nginx
   ```
4. [ ] 用总管理员账号登录后台：右上角显示“总管理员”，左侧有「成员管理」，原来的“总裁/副总裁”切换按钮已消失。订单都还在。
5. [ ] 在「成员管理」创建下属管理员（第一步定好的账号、姓名、密码）。
6. [ ] **执行负责人迁移脚本（只能执行一次）**：打开 `deploy/upgrade_permission_v1_owner_remap.sql`，把最后的 `CALL` 里的账号名改成下属的登录账号再执行。它会：旧负责人 1 → 总管理员、2 → 该下属；清空旧的未读标记；把推送 SendKey 迁到新账号。重复执行会报错中止，是正常保护。
   > 第 3 步到第 6 步之间，订单上显示的“负责人”可能不对，下属还没账号所以不会越权。请尽快做完第 6 步。

## 六、验收（用三个账号各走一遍）

总管理员：
- [ ] 「接单管理」能看到全部订单，负责人显示正确（原副总裁的单显示为下属姓名）。
- [ ] 「客户账号」页有“归属管理员”一列，原有客户都归总管理员；点“转交”能改归属。
- [ ] 「设置」页里每个人的 SendKey 都在（总管理员、下属各一份）。

下属管理员（用新账号登录）：
- [ ] 右上角显示“下属管理员”，没有「成员管理」；地址栏手输 `#/staff` 会被弹回工作台。
- [ ] 「接单管理」只有原来归他的订单，**看不到总管理员的订单**。
- [ ] 极速建单只能建在自己名下，建完总管理员收到提醒。
- [ ] 「设置」页只看到自己的 SendKey，没有全局开关。

客户（任选一个）：
- [ ] 客户端登录正常，只看到自己的项目，聊天、附件、Bug 都正常。
- [ ] 客户提交新需求 → 自动出现在其归属管理员名下（归总管理员的客户→总管理员；转交给下属的客户→该下属）。
- [ ] 客户用这个账号登录后台登录页会被拒绝（提示“该账号不是后台账号”）。

其他：
- [ ] 总管理员在「成员管理」停用下属 → 下属已登录的设备立即下线；再启用后能重新登录。
- [ ] 附件上传下载、`/captchaImage` 正常（`production.md` 原有验收项）。

## 七、回滚

**只做了第 1 步（SQL）**：不用回滚，新表和新角色旧版后端不会用到。

**已切换版本，要退回旧版**：
1. 把 `current` 切回升级前记下的版本目录，`systemctl restart xuancheng-order-backend`，重载 Nginx。
2. 如果**已经执行了第 6 步迁移脚本**，旧版后端认的还是 1/2，需要把数据改回去（把 `<总管理员id>`、`<下属id>` 换成实际 user_id）：
   ```sql
   UPDATE jiedan_order SET owner_id = CASE owner_id WHEN <总管理员id> THEN 1 WHEN <下属id> THEN 2 ELSE owner_id END;
   UPDATE jiedan_order SET unread = '';
   -- 推送 SendKey 改回旧键
   UPDATE jiedan_setting SET setting_key = 'push.sendkey.1' WHERE setting_key = 'push.sendkey.<总管理员id>' AND '<总管理员id>' <> '1';
   UPDATE jiedan_setting SET setting_key = 'push.sendkey.2' WHERE setting_key = 'push.sendkey.<下属id>' AND '<下属id>' <> '2';
   DELETE FROM jiedan_setting WHERE setting_key = 'perm.v1.remapped';
   ```
3. 万一数据乱了：用第三步的备份恢复 `jiedan_order`、`jiedan_setting` 两张表（升级后新增的订单会丢，先导出再恢复）。

## 八、本次不包含 / 已知限制

- 审批流程（第二步）还没做：下属目前仍可把项目状态直接改成“已完成”。
- 图片、视频等附件的访问链接是公开的（靠随机文件名保护），不按订单归属拦截，与升级前一致。
- 本机开发库 `xc_jiedan` 同样要先执行 `upgrade_permission_v1.sql`，新后端才能启动联调。
- 客户提交需求时仍可填报价金额（与升级前一致，未收紧）。
