# 玄成接单系统 · 合并上线手册（权限升级 + 补丁包）

把线上 https://jiedanxt.oksja.cn/ 从现在的旧版，一次升级到 `feat/hardening-v1`（已包含权限升级和上线前补丁包）。

- **这份手册是主线**：照着从上往下做就行。两份详细清单（`权限升级清单.md`、`补丁包升级清单.md`）放在 `docs/`，里面有完整的验收项和回滚细节，手册里用到时会指过去。
- **预计 30 分钟**，其中真正会打不开的只有“重启后端”那一步，约 1 分钟；数据库升级和传文件不影响使用。建议选没人用的时段。
- **为什么要尽快上**：线上旧版有个漏洞——不登录也能往服务器上传文件。这次升级会堵上它。
- 这份手册对服务器的目录、服务名的假设来自 `production.md`，**没有连过真实服务器**。所以第一步先跑体检脚本，结果对得上再往下走；对不上就停下来。

## 零、动手前先定好

- [ ] **时段**。
- [ ] **下属管理员**：登录账号（字母/数字/下划线）、姓名、初始密码。默认是原来的副总裁（费鹏飞）。旧订单里原来归副总裁的单，会转给这个账号。
- [ ] **异地备份目录**：除了服务器本机，最好再有一个地方（另一块盘 / 挂载的网盘 / 另一台机器）。备份和线上在同一块盘上，防得住误操作，防不住磁盘坏。想好目录，第七步要填。

## 一、上线包里有什么

```
xuancheng-release/
├─ 上线手册.md            ← 就是这份
├─ SHA256SUMS.txt         ← 文件校验码（确认传输没出错）
├─ release/               ← 整个目录会变成服务器上的一个新版本目录
│  ├─ admin/              ← 后台网页（admin/client/ 是客户端网页）
│  └─ backend/ruoyi-admin.jar   ← 后端
├─ sql/                   ← 三个数据库脚本
├─ bin/                   ← preflight.sh（只读体检）、backup.sh（自动备份）
└─ docs/                  ← 两份详细清单
```

把 `xuancheng-release.tar.gz` 传到服务器（宝塔文件管理上传，或 `scp`），放在 `/root/` 下，然后：

```bash
cd /root && tar -xzf xuancheng-release.tar.gz
PKG=/root/xuancheng-release
cd $PKG && sha256sum -c SHA256SUMS.txt     # 每一行都应该是 OK
```

> 下面的命令都假设在服务器上、用 root、并且已经执行过上面的 `PKG=...`。如果中途换了终端窗口，记得重新执行这一行。

## 二、服务器体检（只读，不改任何东西）

```bash
bash $PKG/bin/preflight.sh
```

把**全部输出**原样发给我。我对一遍：服务器上的目录、服务、数据是不是和手册假设的一样。**对上之前不要往下做。**

体检结果里，下面三类 `[失败]` 是上线时正好要处理的，不用先解决：

1. Nginx 的 `client_max_body_size` 小于 55m（第四步会改）；
2. 生产配置把上传上限写死成 10MB（第四步会改）；
3. 匿名上传没有被拒绝（升级后才会变成 401）。

其他 `[失败]`（比如服务没运行、连不上数据库、`current` 不是软链接）要先解决。记下体检第 1 段的“`current` 指向”——回滚要用。

## 三、备份（必须）

```bash
mkdir -p /opt/xuancheng-order/backups
mysqldump --defaults-extra-file=/opt/xuancheng-order/config/mysql-root.cnf \
  --single-transaction xc_jiedan \
  > /opt/xuancheng-order/backups/xc_jiedan_before_release_$(date +%F_%H%M).sql
ls -lh /opt/xuancheng-order/backups | tail -3
```

- [ ] 备份文件生成了，大小不是 0。
- [ ] 把这份备份**再复制一份到服务器以外的地方**（下载到自己电脑也行）。

## 四、改 Nginx 和生产配置（体检提示要改才改）

- Nginx：站点配置 `/www/server/panel/vhost/nginx/jiedanxt.oksja.cn.conf` 里 `client_max_body_size` 不小于 `55m`（没有这一行就加上 `client_max_body_size 55m;`）。改完 `nginx -t` 通过，再在宝塔里重载 Nginx。
- 生产配置：`/opt/xuancheng-order/config/application-production.yml` 里如果写了 `max-file-size: 10MB`，改成 `50MB`，`max-request-size` 改成 `55MB`。这个文件改完要在第六步重启后端后才生效。
- 同一个文件里如果有 `statViewServlet` 且 `enabled: true`，改成 `false`。

## 五、升级数据库（只新增字段和表，旧版后端不受影响，可重复执行）

```bash
M="mysql --defaults-extra-file=/opt/xuancheng-order/config/mysql-root.cnf --default-character-set=utf8mb4"
cd $PKG/sql
$M xc_jiedan < upgrade_permission_v1.sql
$M xc_jiedan < upgrade_hardening_v1.sql
$M xc_jiedan -e "show tables like 'jiedan_account_owner'; show tables like 'jiedan_audit_log'; show columns from jiedan_order like 'del_flag'; select role_key, role_name from sys_role;"
```

- [ ] 能看到 `jiedan_account_owner`、`jiedan_audit_log`、`del_flag`，角色里多了 `employee`（名称“下属管理员”，不是乱码）。
- [ ] 订单还在：`$M xc_jiedan -e "select count(*) from jiedan_order"` 的数字和体检里的订单数一致。

> 不要执行 `fresh-install.sql`，它会清空数据。这个包里也没有放它。

## 六、放入新版本、切换、重启

```bash
OLD=$(readlink -f /opt/xuancheng-order/current)      # 旧版本目录，回滚用，请记下: echo $OLD
REL=/opt/xuancheng-order/releases/20261103-release
mkdir -p $REL && cp -a $PKG/release/. $REL/
chown -R --reference="$OLD" $REL                      # 属主与旧版本目录保持一致
chmod -R u+rwX,go+rX $REL
ls $REL $REL/backend $REL/admin | head -20

# 原子切换
ln -sfn $REL /opt/xuancheng-order/current.new && mv -Tf /opt/xuancheng-order/current.new /opt/xuancheng-order/current
systemctl restart xuancheng-order-backend

# 等后端起来（最多约 2 分钟），期望输出 200
for i in $(seq 1 40); do c=$(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:18091/captchaImage); [ "$c" = 200 ] && break; sleep 3; done; echo "后端状态码：$c"
```

- [ ] 输出 `200`。不是 200：看 `journalctl -u xuancheng-order-backend -n 50 --no-pager`，处理不了就直接**回滚**（第十一节），不要硬扛。
- [ ] 不动 `data/`、`uploads/`、`config/`、`logs/`、`backups/`（上面的命令没有碰它们）。
- [ ] 如果第四步改过 Nginx，已经重载过了；静态文件走 `current` 软链接，切换后立即是新版页面（浏览器按 Ctrl+F5 强刷一次）。

## 七、建下属账号 + 迁移旧订单负责人

1. 用总管理员登录后台（`https://jiedanxt.oksja.cn/`，用原来的 admin 账号）。右上角应显示“总管理员”，左侧多了「成员管理」「回收站」「操作日志」，原来的“总裁/副总裁”切换按钮没有了。订单都还在。
2. 「成员管理」→ 新建账号（零里定好的那个下属）。
3. 迁移旧订单的负责人（**只能执行一次**，重复执行会报错中止，是正常保护）。把 `<下属登录账号>` 换成上一步建的账号：

   ```bash
   M="mysql --defaults-extra-file=/opt/xuancheng-order/config/mysql-root.cnf --default-character-set=utf8mb4"
   sed "s/请改成下属的登录账号/<下属登录账号>/" $PKG/sql/upgrade_permission_v1_owner_remap.sql | $M xc_jiedan
   $M xc_jiedan -e "select owner_id, count(*) from jiedan_order group by owner_id"
   ```

   - [ ] 没有报错；负责人分布里出现的是真实账号的 id（不再是 1/2，除非总管理员本来就是 1）。
   - 它做的事：旧负责人 1 → 总管理员、2 → 这个下属；清空旧的未读标记；把微信推送 SendKey 迁到新账号；登记下属的上级。

4. 通知原来共用 admin 账号的副总裁：以后用自己的新账号登录，不要再用 admin。

> 第六步到这一步之间，订单上显示的“负责人”可能不对，但下属还没账号，不会越权。请尽快做完。

## 九、安装自动备份

先在体检结果第 7 段确认附件目录的位置（`jiedan-media` 的上一级就是 `XC_UPLOADS`）。

```bash
mkdir -p /opt/xuancheng-order/bin
cp $PKG/bin/backup.sh /opt/xuancheng-order/bin/backup.sh && chmod +x /opt/xuancheng-order/bin/backup.sh
# 手动跑一次，把两个路径换成真实的；没有异地目录就先去掉 OFFSITE_DIR=...
XC_UPLOADS=<附件目录的上一级> OFFSITE_DIR=<异地目录> /opt/xuancheng-order/bin/backup.sh
```

- [ ] 看到“数据库备份完成”“附件镜像完成”，没有“失败”。
- [ ] 在宝塔「计划任务」（或 `crontab -e`）加两条：

  ```
  30 3 * * *  XC_UPLOADS=<附件目录的上一级> OFFSITE_DIR=<异地目录> /opt/xuancheng-order/bin/backup.sh >> /opt/xuancheng-order/logs/backup.log 2>&1
  0 4 * * 0   VERIFY_RESTORE=1 XC_UPLOADS=<附件目录的上一级> OFFSITE_DIR=<异地目录> /opt/xuancheng-order/bin/backup.sh >> /opt/xuancheng-order/logs/backup.log 2>&1
  ```

  第二条每周日做一次“恢复演练”：把当天备份真的导入临时库验证再删掉。**没演练过的备份不算备份。**

## 十一、回滚

**只做到第五步（数据库）**：不用回滚，新字段和新表旧版后端用不到。

**已经切换版本，要退回旧版**：

```bash
ln -sfn <OLD，第六步记下的旧版本目录> /opt/xuancheng-order/current.new && mv -Tf /opt/xuancheng-order/current.new /opt/xuancheng-order/current
systemctl restart xuancheng-order-backend
```

然后注意三件事（细节在 `docs/` 两份清单的“回滚”一节）：

1. 如果**已经执行了第七步的迁移脚本**，旧版后端认的还是写死的 1/2，需要把订单负责人改回去（SQL 在 `docs/权限升级清单.md` 第七节）。
2. 旧版不认识“回收站”：已经放进回收站的项目，退回后会重新出现在列表里。
3. 退回旧版后，匿名上传漏洞会重新出现，请尽快修好后再升级。

数据本身乱了：用第三步的备份恢复（升级后新增的订单会丢，先导出再恢复）。
